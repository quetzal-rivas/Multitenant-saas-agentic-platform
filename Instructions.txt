# Role
You are a senior backend engineer working inside my existing codebase. Follow the conventions already in this repo (language, framework, ORM, migrations, naming, testing). Do not add new frameworks or major dependencies without asking.

# Product context
This platform lets users create AI agents. An agent is instantiated from an MCP profile (tools) plus a context profile (skills and system prompts). Agents can be single (monolithic) or a team: a supervisor with sub-agents that only run when the supervisor triggers them. Supervisors are currently run on demand only. There is NO heartbeat yet, NO organization concept, and NO board. Do not assume any of them exist.

# Goal
Build three things, in this order:
1. A heartbeat: a way to wake a supervisor on a schedule so it works proactively against its goal.
2. A minimal organization scope: just an `org_id` used to group supervisors.
3. A board scoped to that org where separate supervisors coordinate (post tasks, claim tasks, post results).

# Step 0: Explore first (no code)
Summarize how supervisors are created and executed today: the run entry point, how the agent loop calls tools, how MCP profiles and context profiles are attached, and where run state or logs are stored. Then propose a short plan and wait for my confirmation if anything is ambiguous. Reuse the existing run path for heartbeat runs; do not create a parallel execution system.

# Part 1: Heartbeat
- Add per-supervisor heartbeat config: enabled flag, interval, optional active hours, and a goal/checklist (text the supervisor reads on each beat and can update).
- Add a scheduler that enqueues a "run" for each due supervisor. A heartbeat run must go through the same run path as a manual run, tagged with trigger type `heartbeat`, so other triggers (cron, webhook, user message) can be added later without changes.
- Cheap check before the full run: if the goal/checklist has nothing pending and there is nothing new to act on, skip the expensive model run and record a no-op. No-ops should be silent to the user.
- Per-supervisor lock so a slow run never overlaps with the next beat.
- Guardrails: max tool calls per run, a per-run and per-day cost or token cap, and jitter on scheduling.
- Log every beat (started, no-op, completed, failed, cost, tools called) so runs can be inspected later.
- A pause/disable switch per supervisor.

# Part 2: Minimal organization scope
- Add an `organizations` table (id, name, created_at) and a required `org_id` on supervisors.
- Auto-create one org per account on signup, and backfill one org per existing account in a migration before adding the NOT NULL constraint.
- That is all. Do NOT build membership tables, roles, invitations, permissions, org switching, or any logic for giving one account access to another account's data. The only purpose of org_id right now is to scope the board.

# Part 3: Org board (supervisor to supervisor)
Tables:
- `board_tasks`: id, org_id, created_by_supervisor_id, title, description, status (`open`, `claimed`, `in_progress`, `done`, `failed`, `cancelled`), claimed_by_supervisor_id (nullable), lease_expires_at (nullable), result (nullable), created_at, updated_at.
- `board_events`: append-only log of every state change (task_id, supervisor_id, event_type, payload, created_at).

Behavior:
- Claiming is atomic (conditional update or transaction with locking) so two supervisors can never claim the same task.
- Claims have a lease. If it expires without completion, the task returns to `open`. Make the requeue function idempotent and callable from the heartbeat or a sweeper. Allow lease renewal.
- Only the claimer can complete or fail a task; the creator can cancel.
- A supervisor can only see and touch tasks with its own org_id. Derive org_id from the supervisor's own record, never from client or model input.
- Task creation accepts an idempotency key so a retried heartbeat doesn't create duplicates.
- Expose the board to supervisors as agent tools (e.g. `board_list_tasks`, `board_create_task`, `board_claim_task`, `board_renew_lease`, `board_complete_task`, `board_fail_task`), registered the same way existing tools are.
- Heartbeat integration: the cheap check also looks for open board tasks in the org and the supervisor's own claimed tasks nearing lease expiry, and board tools are available inside heartbeat runs.
- Treat all board text as untrusted input. A task written by one supervisor must never grant another supervisor new tools or credentials, and secrets must never appear in board payloads.

# Out of scope: do not build
Dashboard or any UI (backend and API only, expose data cleanly so a dashboard can be added later), org membership and roles, invitations, multi-org per account, cross-account or cross-org sharing, franchise/shared boards, public commons, approvals, per-seat billing. If one of these forces a design decision, pick the option that keeps it possible later and tell me.
