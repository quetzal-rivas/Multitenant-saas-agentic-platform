 ### The important distinction

 **More open-ended:**

 > "Here are the building blocks. Build your own AI system."

 versus

 **More constrained:**

 > "Here are 10 things our platform supports. Configure them in different ways."

 Context Control seems to be **somewhere in between**.

 ### But there are still layers of limitations

 Even if the underlying AI agents are flexible, you're still dependent on what **Context Control itself exposes**:

 - What kinds of agents can you create?
- Can you write arbitrary agent logic, or only configure prompts?
- Can agents execute arbitrary code?
- Can you install/connect your own MCP servers?

- Can agents maintain persistent state/memory?

- Are there limits on tokens, calls, voice minutes, etc.?
- Can you self-host it?
- Can you export what you've built and run it somewhere else?

 Those answers determine whether it's genuinely a **general-purpose AI development platform** or primarily a **no/low-code automation product**.

 Description

Turn the documentation pages of this Next.js project into a routed skill (a short SKILL.md plus small topic files). Use when the user asks to create, generate, rebuild, or refresh a skill from the docs, or invokes /docs-to-skill.

Docs to Skill

Build a skill that lets an assistant answer questions about this project's documentation by loading only the pages a question needs, instead of the whole site.

Inputs

Ask the user only for what you cannot find yourself:

Docs location. Look first in app/docs, pages/docs, content/docs, docs/, or any folder of .md / .mdx files or route files under a /docs path. If several candidates exist, ask which one is the documentation.
Skill name. Default to <project-name>-docs in kebab-case (from package.json).
Output folder. Default to .claude/skills/<skill-name>/. If it already exists, ask before overwriting.
Steps
1. Inventory the docs

List every documentation page with its source file, its route (for example /docs/api/auth), its title, and its headings. If pages are React components (page.tsx) rather than markdown, read the rendered text content and code samples from the component, ignoring layout and styling code. Record any page you cannot read and report it at the end.

2. Group into topics

Group pages by what a user would ask about (getting started, authentication, endpoints, deployment, troubleshooting, and so on). Aim for one topic per file, roughly 50 to 300 lines each. Split a long page by its top-level headings; merge tiny related pages. Keep the original order inside each file.

3. Convert to plain markdown

For each topic file:

Start with a title and a Source: line listing the original file path and route, so answers can point to the real page.
Keep prose, tables, and code blocks exactly as written. Do not summarize, reword, or "improve" the content.
Remove JSX imports, layout wrappers, and interactive components. Where a component carries meaning (a callout, a tabbed code sample), replace it with the equivalent plain markdown.
Fix relative links so they point to other topic files or to the site route.
Never copy secrets, tokens, or real environment values. Keep placeholder examples.
4. Write the folder
<skill-name>/
  SKILL.md        # short router (see template below)
  index.md        # every page: route, one-line summary, topic file
  <topic>.md      # one file per topic, in subfolders if there are many

If the docs are large (more than about 30 files), use subfolders that mirror the site sections.

5. Write the generated SKILL.md

Keep it under about 100 lines. Use this template:

markdown
---
name: <skill-name>
description: <One or two sentences on what the docs cover, plus concrete trigger phrases, e.g. "Use when the user asks about <Product> setup, API, authentication, deployment, or errors.">
---

# <Product> documentation

Snapshot of the docs generated on <date> from <source path>. Live site: <base URL if known>.

## How to use
Read only the file that matches the question. Cite the `Source:` route when answering. If nothing matches, read `index.md`, then search this folder for keywords before saying the docs do not cover it.

## Routing
| Question is about | Read |
|---|---|
| <topic> | <topic>.md |
...

## Freshness
This is a copy. If the answer could depend on recent changes, say the docs snapshot may be out of date and point to the live page.

The description is what triggers the skill, so make it specific to this product and its topics.

6. Optional sync script

If the user wants to refresh the skill later, add scripts/sync-docs.mjs to the project that regenerates the topic files from the docs source and updates the date in the generated SKILL.md. Do not add it unless asked.

Before reporting done, check and fix:

Every source page appears in index.md and in exactly one topic file.
Every row in the routing table points to a file that exists.
No topic file has broken relative links.
The generated SKILL.md is short and its description names real topics.
Test with three sample questions taken from the docs: confirm the routing table sends each one to the right file and that the file contains the answer.
